# 폴더 구조 표준

JRI 연구과제 작업 폴더(공유드라이브 기준) 표준 구조.

## 운영 원칙

1. **10단위 넘버링.** 1단위로 매기면 사이에 슬롯을 끼워넣을 때 전부 리네이밍해야 함. 10단위면 11, 12, … 로 자유롭게 추가 가능.
2. **00과 99는 양 끝의 고정 슬롯.** 새 슬롯이 늘어나도 위치가 흔들리지 않음.
3. **공통 슬롯만 표준화.** 과제 성격에 따라 달라지는 부분은 선택 슬롯으로 유지.
4. **분류 축은 하나.** 표준의 축은 **연구 진행 단계**임. 주제·문서종류·시간 같은 다른 축을 최상위에 섞으면 슬롯이 늘어나면서 어디를 봐야 할지 알 수 없게 됨. 자세한 것은 「수행 구간을 나누는 기준」 참조.

## 표준 슬롯

### 필수

| 번호 | 이름 | 역할 |
|---|---|---|
| **00** | RFP 또는 과제기획 | 과제 유형에 따라 갈림 — 아래 「00 슬롯의 두 갈래」 참조. **수정 금지**. |
| **01** | code | 분석 코드/스크립트/노트북. Git 관리 대상. |
| **10** | 연구설계심의 | `research_plan.docx`, IRB, 연구설계 심의 자료. |
| **20** | 회의 | 회의록, 자문회의록, 실무 간담회 자료, 발표 슬라이드. |
| **30** | data (또는 핵심문서) | 1차 자료, 통계 원자료, 설문 응답, 정성 자료. 과제 성격에 따라 `30.data` 또는 `30.핵심문서`. |
| **50** | 중간보고 | 중간보고서 본문, 발표자료, 검토의견서. |
| **80** | 행정 | 계약서, 정산 자료, 공문, 인사관리. |
| **90** | 최종보고서 | 최종보고서 본문, 출판본, 인쇄용 원고. |
| **99** | Reference (또는 참조문헌) | 선행연구, 참고문헌, 외부 보고서. |

### 00 슬롯의 두 갈래

`00` 은 「밖에서 들어온, 우리가 고칠 수 없는 착수 문서」 자리임. 그런데 그 문서의 정체가 과제 유형에 따라 다름.

| 과제 유형 | 슬롯 이름 | 들어가는 것 |
|---|---|---|
| 수탁·공모 | `00.RFP` | 발주처 RFP, 수요조사서, 제안요청서 원본 |
| 내부·기획 (미래기획, 기반과제 등) | `00.과제기획` | 내부과제수행계획서, 과제 제안서, 예산·기간 변경본 |

내부과제에는 발주처가 없어 RFP 자체가 존재하지 않음. 이때 `00.RFP` 라는 이름을 쓰면 **폴더 이름이 내용과 어긋남** — 실제로 한 미래기획과제에서 `00.RFP` 에 수행계획서가 들어 있고, 정작 발주용 RFP 는 30번대에 있어 두 폴더가 이름만 보면 정반대로 읽히는 상태가 발생했음.

`init_project.sh --type 내부` 로 생성하면 `00.과제기획` 이 만들어짐.

### 선택

| 번호 | 이름 | 사용 예 |
|---|---|---|
| 40 | RIO / 모형 / 시뮬레이션 | 산업연관분석(RIO), 시스템 다이내믹스, CGE 등 특수 분석 산출물. |
| 40 | 실증·운영 | **정보화·시스템 과제 전용.** 연구 기간 중 실제로 도입·전환·운영한 것. 도구 세팅, 시스템 전환 실무, 운영 규범. |
| 45 | 발주설계 | **정보화·시스템 과제 전용.** 기능요구사항(SFR), 발주 RFP, TO-BE 설계. `50.중간보고` 가 고정이라 반 칸으로 둠. |
| 91 | 보도자료 | 보도자료 초안, 언론배포 자료. |
| **98** | 선행TF / 인수자료 | 이전 TF·전임자·선행 조직에서 넘어온 자료. `99.Reference`(외부 자료)와 성격이 달라 구분함. 실물이 다른 연도 폴더에 있으면 심링크로 두어도 됨. |
| 60, 70 | (예비) | 중간보고와 최종보고 사이에 추가 산출물(예: 워크숍 결과, 1·2차 중간 발표)을 두고 싶을 때. |

## 수행 구간을 나누는 기준

`20`〜`45` 는 「과제를 실제로 수행하면서 쌓인 것」이 들어가는 구간이고, 과제가 커질수록 여기가 먼저 무너짐. 자료가 늘면 주제별로 폴더를 하나씩 더 만들게 되는데, 그렇게 늘어난 슬롯은 서로 배타적이지 않아 같은 성격의 자료가 여러 곳에 흩어짐.

**규칙 — 수행 구간의 하위 갈래는 3개를 넘기지 않고, 그 기준은 최종보고서의 서사에서 가져옴.**

과제가 끝날 무렵 보고서 목차가 이미 그 과제의 가장 좋은 분류 체계임. 목차를 폴더에 그대로 쓰면 자료를 찾는 사람이 「무엇을 알아냈나 / 무엇을 해봤나 / 무엇을 만들었나」 로 물어볼 수 있음.

정보화 과제의 실례.

```
30.진단        무엇을 알아냈나   설문·실태조사·현행시스템 분석·기관 제도
40.실증·운영   무엇을 해봤나     도구 세팅·시스템 전환·운영 규범
45.발주설계    무엇을 만들었나   기능요구사항·RFP·TO-BE 설계
```

**늘리지 말아야 할 신호.** 새 폴더를 만들기 전에 아래를 확인함.

- 새로 만들려는 폴더가 기존 슬롯과 **배타적인가.** 「설문조사」와 「구시스템 조사」는 배타적이지 않음 — 둘 다 진단임.
- 그 폴더를 **1년 뒤에도 같은 이름으로 부를 것인가.** 「~관련」, 「~준비」 가 이름에 붙으면 대개 임시 분류임.
- 최상위 대신 **하위 폴더로 충분하지 않은가.** `30.진단/_설문조사` 로 될 일을 `28.설문조사(원내)` 로 올리지 않음.

## 명명 규칙

### 최상위

- 폴더명은 `NN.한글이름` 형식. 점(`.`) 뒤에 공백 없이 한글.
- 영문 통일 슬롯(예: `01.code`, `30.data`, `99.Reference`)은 그대로 유지. 과제 책임자가 이전 프로젝트와의 일관성을 우선 고려해 한글/영문 중 택일.
- 상위 과제 폴더명: `YYYYMMDD_구분_과제명` (예: `20260601_정책_아트페스타인제주경제효과`).

### 하위

| 형식 | 뜻 | 예 |
|---|---|---|
| `_밑줄` 접두 | 분류용 하위 폴더 | `_설문조사`, `_기관제도`, `_운영규범` |
| `YYYYMMDD_` 접두 | 사건·회의 단위 폴더 | `20260114_RFP2차회의` |
| `_archive` | 구버전. 각 슬롯 안에 둠 | `50.중간보고/_archive` |

- 파일명의 날짜는 `YYMMDD_` 6자리로 통일. 8자리와 섞으면 정렬이 어긋남.
